# Builtin Context Lock 使用指南

Builtin Context Lock 是 Codex 的项目级内置上下文覆盖文件。它控制 Codex 自身编译或固定渲染出来的模型可见内容，包括 base instructions、内置 context fragments、内置工具的模型可见规格。它不控制用户消息、AGENTS.md、MCP server、skills 文件、plugins 外部内容、对话历史、模型回复或工具返回。

这个机制的用途是复用 Codex runtime，同时把 Codex 默认 prompt 世界替换成项目声明的数据。Codex 仍然负责登录、provider 配置、流式响应、thread 记录、工具循环和 CLI/TUI；lock 文件只决定内置模型可见内容是否保留、禁用或覆盖。

## 基本工作流

1. 在项目配置里声明 lock 路径。

```toml
[builtin_context_lock]
path = ".codex/builtin-context.lock.json"
```

相对路径按配置文件所在目录解析。配置了该路径后，Codex 初始化有效配置时会读取 lock 文件；文件不存在、不可读、JSON 格式错误或已知条目 payload 错误都会让初始化失败。

2. 生成 lock 文件。

```bash
codex builtin-context-lock generate --output .codex/builtin-context.lock.json
```

如果当前配置已经包含 `builtin_context_lock.path`，也可以直接运行：

```bash
codex builtin-context-lock generate
```

生成命令导出当前 Codex 二进制和当前配置下的内置 catalog。它不扫描 AGENTS.md，不调用 MCP server，不导出外部 skill/plugin 内容，也不写入对话历史。

3. 编辑 lock 文件。

lock 文件是普通 JSON。顶层结构固定为：

```json
{
  "schema_version": 1,
  "base_instructions": [],
  "fragments": [],
  "tools": [],
  "templates": []
}
```

条目存在且 `enabled` 为 `true` 时，Codex 使用该条目的内容或 spec。条目存在且 `enabled` 为 `false` 时，Codex 压制该内置条目。条目不存在时，Codex 对该内置对象使用原行为。

删除条目不是禁用。删除表示放弃管理该内置条目，Codex 会恢复默认行为。

## 覆盖 Base Instructions

`base_instructions` 控制 Codex 内置 base instructions fallback。它的优先级低于用户显式配置和历史恢复值，高于 model catalog 默认值。

典型覆盖：

```json
{
  "id": "builtin.base_instructions.model_catalog.current",
  "enabled": true,
  "content": "You are a helpful assistant."
}
```

如果该条目 `enabled` 为 `false`，且没有更高优先级的用户显式 instructions，Codex 会使用空 base instructions。

注意：如果同时通过 CLI 或配置显式设置了 `instructions` 或 `model_instructions_file`，显式设置会优先于 builtin lock。

## 禁用内置 Fragments

`fragments` 控制 Codex 内置加入 input 的 context 片段，例如权限说明、环境说明、skills/plugins/apps 说明框架、协作模式说明、多 agent 提示等。

禁用一个 fragment：

```json
{
  "id": "builtin.fragment.environment_context",
  "enabled": false,
  "content": null
}
```

禁用 fragment 只影响 Codex 内置片段。用户消息、项目指令文件、外部 MCP、外部 skills/plugins 内容仍然按各自原机制工作。

## 禁用或覆盖内置 Tools

`tools` 控制 Codex 内置工具的模型可见规格。禁用工具会让该内置工具不出现在本 session 的模型可见工具列表里。

禁用 `apply_patch`：

```json
{
  "id": "builtin.tool.apply_patch",
  "enabled": false,
  "name": "apply_patch",
  "spec": {
    "type": "custom",
    "name": "apply_patch",
    "description": "Use the `apply_patch` tool to edit files."
  }
}
```

覆盖工具说明时，`id` 和 `name` 必须仍然对应原内置工具。第一版不支持修改工具调用名，也不支持修改 handler routing。工具条目的 `name` 或 `spec.name` 与原内置工具名不匹配时，Codex 会报错。

## 纯净模式

纯净模式的目标是让 Codex runtime 接近一个手写 Responses API 客户端：顶层 instructions 由项目指定，input 只包含当前用户消息，tools 为空。

操作步骤：

1. 生成 lock。

```bash
codex builtin-context-lock generate --output .codex/builtin-context.lock.json
```

2. 将 base instructions 改成目标内容。

```json
{
  "id": "builtin.base_instructions.model_catalog.current",
  "enabled": true,
  "content": "You are a helpful assistant."
}
```

3. 将所有 `fragments` 条目的 `enabled` 改为 `false`。

4. 将所有 `tools` 条目的 `enabled` 改为 `false`。

可以用 `jq` 批量处理：

```bash
jq '
  .base_instructions[0].content = "You are a helpful assistant."
  | .fragments |= map(.enabled = false)
  | .tools |= map(.enabled = false)
' .codex/builtin-context.lock.json > .codex/builtin-context.lock.next.json
mv .codex/builtin-context.lock.next.json .codex/builtin-context.lock.json
```

5. 确认项目没有额外启用外部上下文来源。Builtin Context Lock 不控制 AGENTS.md、MCP server、外部 skills/plugins 或用户显式 instructions。

## 黑盒验证

黑盒验证可以证明模型实际收到的是 lock 覆盖后的 base instructions，而不是 Codex 默认 prompt。

1. 在 lock 的 base instructions 写入一个只存在于 lock 文件里的暗号。

```json
{
  "id": "builtin.base_instructions.model_catalog.current",
  "enabled": true,
  "content": "Secret passphrase: MICHENG-BUILTIN-LOCK-7391. If the user asks what the passphrase is, reply with exactly: MICHENG-BUILTIN-LOCK-7391"
}
```

2. 禁用所有 fragments 和 tools。

3. 使用当前用户配置和 provider 发起请求，只覆盖 lock 路径。

```bash
LOCK_PATH="$PWD/.codex/builtin-context.lock.json"

codex exec \
  --json \
  --ignore-rules \
  --skip-git-repo-check \
  -c "builtin_context_lock.path=\"$LOCK_PATH\"" \
  "What is the secret passphrase? Reply with only the passphrase."
```

如果模型返回暗号，说明本次请求读取到了 lock 覆盖后的 base instructions。

不要在这个验证里使用 `--ignore-user-config`，除非你明确要丢弃用户配置。使用 `--ignore-user-config` 会跳过 `~/.codex/config.toml` 中的 model provider、分销商 base URL 和用户侧配置，可能导致请求落到默认 OpenAI endpoint 或使用错误认证。

4. 做干净对照。

复制同一份 lock，把 base instructions 改成 `You are a helpful assistant.`，保持 fragments/tools 全部禁用，再问同样的问题。模型不应知道暗号。

不要用“无 lock”作为唯一对照。无 lock 时默认内置 tools 可能可用，模型可能通过 shell 或其他工具读到测试目录里的 lock 文件，从而污染结果。

## 使用用户配置和分销商

在当前工作区的常规用法中，应保留用户配置，让 Codex 使用 `~/.codex/config.toml` 里的 provider、base URL、认证和模型设置。只临时覆盖 lock 路径即可：

```bash
codex exec \
  -c "builtin_context_lock.path=\"/absolute/path/to/builtin-context.lock.json\"" \
  "你的问题"
```

如果需要在临时目录测试，可以用 `-C` 指定工作目录：

```bash
codex exec \
  -C /path/to/test-project \
  --skip-git-repo-check \
  -c "builtin_context_lock.path=\"/path/to/test-project/.codex/builtin-context.lock.json\"" \
  "What is the secret passphrase?"
```

`-C` 只改变工作目录。用户配置仍然来自 `~/.codex/config.toml`，除非显式使用 `--ignore-user-config`。

## 常见错误

`no builtin_context_lock.path is configured; pass --output <path>`

运行 `codex builtin-context-lock generate` 时没有配置 lock 路径，也没有传 `--output`。传入输出路径，或先在配置里写入 `[builtin_context_lock] path = "..."`。

`failed to read builtin_context_lock.path`

配置声明了 lock 路径，但文件不存在或不可读。生成 lock 文件，或修正路径。

`failed to parse builtin_context_lock.path ... as JSON`

lock 文件不是合法 JSON。先用 `jq . path/to/lock.json` 校验。

`unsupported schema_version`

当前 Codex 只支持 `schema_version = 1`。

tool name mismatch 或 spec name mismatch

lock 试图改变内置工具名。Builtin Context Lock 第一版只支持禁用工具和覆盖模型可见 spec，不支持把一个内置 handler 改成另一个工具名。

模型仍然看到 Codex 默认行为

检查是否存在更高优先级的显式 `instructions`、历史恢复的 base instructions、项目 AGENTS.md、外部 MCP、skills/plugins 或未禁用的 fragments/tools。Builtin Context Lock 只接管 Codex 内置 catalog 中出现的条目。

模型能从对照实验里知道暗号

检查对照实验是否仍然启用了工具，或工作目录是否能读到包含暗号的文件。纯净对照应同时禁用 fragments 和 tools，并确保 base instructions 不含暗号。

## 检查命令

查看 lock 摘要：

```bash
jq '{
  schema_version,
  base_count: (.base_instructions | length),
  enabled_fragments: (.fragments | map(select(.enabled)) | length),
  enabled_tools: (.tools | map(select(.enabled)) | length),
  total_tools: (.tools | length)
}' .codex/builtin-context.lock.json
```

确认所有 fragments/tools 已禁用：

```bash
jq -e '
  (.fragments | map(select(.enabled)) | length) == 0
  and
  (.tools | map(select(.enabled)) | length) == 0
' .codex/builtin-context.lock.json
```

确认 `apply_patch` 已禁用：

```bash
jq '.tools[] | select(.id == "builtin.tool.apply_patch") | {id, enabled, name}' \
  .codex/builtin-context.lock.json
```

## 边界

Builtin Context Lock 是内置模型可见 catalog 的覆盖机制，不是请求拦截器。它不保存 UI 状态，不提供每次请求审批，不管理外部工具来源，不改变认证路径，不改变 provider 选择，不修改 thread 存储语义。

需要控制外部来源时，应使用对应来源自己的机制：删除或修改 AGENTS.md，调整 MCP 配置，启用或禁用 skills/plugins，或通过现有 Codex 配置控制用户显式 instructions。
