## Product Contract

Builtin Context Lock is a project-level file that can override or disable Codex built-in model-visible content while leaving the runtime intact.

The lock controls only Codex built-in model-visible sources:

- built-in base/model instructions fallback
- built-in context fragments generated by Rust code
- built-in tool specs and model-visible tool definitions
- optionally templates when useful, but template support is not required for the first complete version

The lock does not control:

- AGENTS.md
- MCP server dynamic tools
- skills or plugin content
- user messages, model replies, tool results, thread metadata, rollout metadata, transport state
- runtime approval UI or final request interception

Runtime semantics:

- If an entry exists with `enabled: true`, use the lock payload for that built-in object.
- If an entry exists with `enabled: false`, suppress that built-in object.
- If an entry is missing, preserve original Codex behavior.
- Unknown ids should be ignored with a warning.
- Malformed payload for a known id should fail clearly.
- Tool id/name mismatch must fail clearly.

Default behavior with no configured lock path must be unchanged.

## Suggested Architecture

Create a small module for Builtin Context Lock rather than spreading JSON parsing through call sites. Good candidate locations:

- Runtime module in `codex-rs/core/src/builtin_context_lock.rs`, or a small new crate only if dependencies make that necessary.
- Config TOML shape in `codex-rs/config/src/config_toml.rs`.

The runtime module should own:

- lock file structs with `schema_version`
- entry structs for base instructions, fragments, tools, and possibly templates
- stable ids as constants or typed enums
- known-id inventory shared by runtime application and generate command
- parsing/validation from path
- lookup helpers:
  - `base_instructions_decision(id)`
  - `fragment_decision(id)`
  - `tool_decision(id, original_tool_name)`

Avoid stringly typed checks at every call site. The stable ids are the contract; keep them centralized.

For tools, consider adding a wrapper to `ToolRegistryBuilder`, for example a built-in registration method that:

- receives the known builtin id and handler
- checks lock decision
- skips registration for disabled built-in tools
- registers the original handler with an overridden spec for enabled override

Do not apply this to MCP/dynamic/extension registrations.

For fragments, consider small helpers that apply a decision around section pushes:

- disabled: do not push
- enabled with content: push that content into the same role/section class
- enabled without content: push original rendered text
- missing: push original rendered text

Keep role fixed. Do not let lock change fragment role.

## Phase Plan

### Phase 1: Config And Lock Parser

Deliverables:

- TOML config supports:

```toml
[builtin_context_lock]
path = ".codex/builtin-context.lock.json"
```

- Effective `Config` carries a resolved lock path and parsed lock state, or enough information for session/tool construction to load it once.
- Path resolution must be consistent with existing project config path rules. Document the chosen rule in code comments or tests.
- Missing/unreadable/malformed configured lock fails session/config initialization clearly.
- Unsupported `schema_version` fails clearly.
- Unknown ids are accepted with warning.

Tests:

- config loads the TOML table and path
- malformed JSON fails
- unsupported schema version fails
- unknown id does not fail

Commit after this phase.

### Phase 2: Base Instructions

Deliverables:

- Builtin lock can override built-in model fallback base instructions.
- User explicit base instructions still win.
- Resumed/forked history base instructions still win over builtin fallback.
- Disabled base entry produces empty base instructions when no higher-priority source exists.
- No configured lock keeps current behavior.

Tests:

- explicit `instructions` beats lock content
- lock content applies when there is no explicit override/history
- disabled base entry yields empty string
- no lock preserves model catalog fallback

Commit after this phase.

### Phase 3: Built-In Tool Locking

Deliverables:

- Known built-in tools have centralized ids.
- Lock can disable a built-in tool so it disappears from `model_visible_specs()` and is not registered as callable for the session.
- Lock can override a built-in tool model-visible spec/description while retaining original tool name and handler routing.
- Tool name mismatch for a known builtin id fails clearly.
- MCP/dynamic/extension tools are not affected.

Tests:

- disabling `builtin.tool.apply_patch` removes `apply_patch` from model-visible specs and other unmanaged built-ins remain
- overriding a built-in tool description changes the visible spec and preserves name
- name mismatch errors
- at least one MCP/dynamic/extension path remains unaffected if a suitable existing test utility exists

Commit after this phase.

### Phase 4: Built-In Fragment Locking And Pure Mode

Deliverables:

- Lock can suppress major built-in fragments in `build_initial_context`.
- Lock content override works for static fragments where practical.
- External sources are not suppressed:
  - AGENTS/project user instructions
  - MCP/plugin/skill actual external entries
  - extension contributors unless they are explicitly Codex built-ins
- Pure mode regression test can construct a request where:
  - instructions are `You are a helpful assistant.`
  - tools are empty
  - input contains the user message
  - input does not contain permissions/collaboration/environment/skills/plugins/apps built-in fragments

Tests:

- pure mode regression test from design section 17
- individual fragment disable test for at least permissions and environment context
- no lock preserves existing initial context behavior

Commit after this phase.

### Phase 5: Generate Command

Deliverables:

- `codex builtin-context-lock generate`
- If configured path exists, default output is that path.
- If no configured path exists, require `--output <path>` and fail with clear usage/error when missing.
- Command writes JSON with:
  - `schema_version: 1`
  - `base_instructions`
  - `fragments`
  - `tools`
  - `templates` if implemented, otherwise an empty array
- Generated enabled states reflect current default behavior for generated entries.
- Command does not enable config, start UI, write sidecars, scan AGENTS.md, call MCP `list_tools`, read skill files, or export user history.

Tests:

- CLI/generation unit or integration test for output shape
- no configured path and no `--output` fails
- configured path output works or command helper test proves path selection

Commit after this phase.
