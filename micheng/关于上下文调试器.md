# 如果目标是“运行时完全掌控 Codex 上下文”，最干净的完整做法是什么

我理解你现在要的不是一个简单的“prompt override”。你要的是一个运行时可视化调试系统：Codex 每一刻准备发给模型什么、为什么会出现这些内容、它们从哪个源头来、哪些是官方默认、哪些是 AGENTS、哪些是工具说明、哪些是历史、哪些是 compaction、哪些是权限策略生成的 developer block，这些都要结构化暴露；而且你不仅要看，还要能暂停、手动修改、覆盖、删除、重排，甚至改变拼装逻辑本身。你希望模型实际收到的东西不是一个不可见的黑箱，不是“官方默认值在某个角落悄悄塞进来”，而是一个你可观察、可解释、可控制的运行时对象。

这个诉求我觉得非常成立，尤其是在科研、prompt 行为研究、agent 安全、上下文污染分析、工具调用审计、模型差异实验这些场景里。Codex 默认的目标是“帮助用户完成代码任务”，所以它会主动塞一堆对工程任务有利的上下文：coding-agent 身份、编辑规范、AGENTS.md、权限说明、沙箱说明、工具说明、协作模式、skills、plugins、环境信息、历史摘要、thread resume 信息。这些对一般代码任务是合理的，但对科研实验就是噪声。你要做的是把 Codex 从“产品化 agent 客户端”变成“可仪器化的 agent runtime”。这个方向不是小修小补，而是一个调试/实验控制平面。

我会先给结论：

**最干净、最完整的做法不是只在最后请求前做一个 JSON 拦截器，也不是到处改内置 prompt，而是引入一个正式的 Runtime Context Control Plane。它分三层：Context Provenance Trace、Context Assembly Policy、Outbound Request Gate。**

这三层分别解决三个问题：

1. **Context Provenance Trace：我看到的每段上下文从哪里来，为什么出现？**
2. **Context Assembly Policy：运行时应该怎样拼上下文，哪些源头启用，哪些源头禁用，哪些源头改写？**
3. **Outbound Request Gate：最终发给模型前，我是否允许、改写、替换、阻断？**

只有第三层是“最后一公里拦截”。它很强，但它只能告诉你最终是什么，不能充分解释为什么。只有第一层是“追踪”。它能解释，但不能改变行为。只有第二层是“真正改变拼装逻辑”。它让你在运行时改变 Codex 的上下文生成规则，而不是只对结果打补丁。

所以我认为，如果你要做“最完整”，不要把系统设计成一个简单的代理或抓包工具，而要把它做成 Codex 内部的一个调试控制平面：Codex 仍然正常运行，但每一个 context fragment 都带 provenance；每一个 assembly decision 都可被 runtime policy 控制；每一个 outbound request 都必须经过可视化 gate。

## 一、为什么只拦最终请求还不够完整

我上一条已经说过，最终请求拦截是一个非常好的第一版。它的位置干净，改动少，价值高。你可以在 `ResponsesApiRequest` 发送前看到 `instructions`、`input`、`tools`，然后手动改写。这已经能保证“模型实际收到什么我知道”。

但你现在提出的目标比这个更深。你说“甚至能改变它的拼装逻辑”。这就不是最终请求拦截能优雅解决的了。

举个例子：假设你发现 `input` 里有一段 `<permissions instructions>`。最终请求 gate 可以删除它，这次请求没问题。但下一轮 Codex 可能又把它拼回来，因为内部 `include_permissions_instructions` 仍然是 true。你可以每次都在 gate 里删，但这只是结果层 patch。它不能表达“这个 thread 从现在开始不要生成 permissions instructions”。

再比如 `AGENTS.md`。最终请求 gate 可以删掉某个 AGENTS block。但 Codex 内部仍然认为 user_instructions 存在，后续 context diff 或 resume reconstruction 可能继续带它。你要的是运行时策略：“禁用 AGENTS.md 注入”、“只允许当前 cwd 的 AGENTS，不允许父级”、“把 AGENTS 作为普通 user context 而不是 developer context”、“把 AGENTS 内容降权为 debug note”。这些都属于拼装策略，不是简单删除字符串。

再比如 tools。最终请求 gate 可以把 `tools` 改掉，但 Codex 内部仍然以为某个工具可用。模型如果不再看到工具，后续 Codex 的 tool call handling 可能没问题；但如果你改了工具 schema 或工具名称，内部 dispatch 可能不匹配。更干净的是在 tool registry 到 prompt tool spec 之间加 policy：哪些工具可暴露，schema 是否压缩，description 是否改写，是否把工具放入某个实验组。

再比如 thread history。你可以在最终请求里删除过去 N 轮历史。但 Codex 的 context manager 仍然认为这些 history 在内部存在。下轮 compaction、token estimate、resume/fork 可能还是依据原始历史。你真正需要的是一个 history selection policy：本轮发送哪些历史项、哪些折叠、哪些遮蔽、哪些改写、哪些只用于本地状态但不发给模型。

所以完整系统一定要超越“最后请求 JSON 编辑器”。最终 gate 是保险丝和最终确认，但不是唯一控制点。

## 二、我建议的完整架构：Runtime Context Control Plane

我会把它命名成类似 `codex-context-lab` 或 `runtime_context_control`。它不是一个普通 feature，而是一个 debug/instrumentation mode。它由 Codex 内部 runtime hook、一个本地后端、一个浏览器 UI 三部分组成。

### 1. Codex 内部 runtime hook

这是 Rust 侧的核心。它要在几个关键节点发出事件，或者请求决策：

- context source loaded：某个源头被读取了，比如 AGENTS.md、skill、plugin、model catalog、thread metadata。
- context fragment rendered：某个 fragment 被渲染成 developer/user/context item。
- context assembly planned：本轮准备把哪些 fragment 放入 initial context 或 update items。
- prompt built：`Prompt { input, tools, base_instructions }` 已生成。
- responses request built：`ResponsesApiRequest` 已生成。
- outbound request decision needed：发送前等待 allow/rewrite/deny。
- request sent / response received / tool call emitted / history appended。

这些事件不是都要阻塞。大部分是 observe event，只有少数是 decision point。

### 2. 本地后端

后端负责接收事件、保存结构化记录、维护 runtime policy、处理 pending approval。它应该有自己的 SQLite，独立于 Codex 的 rollout。原因很重要：你不应该把 debug 记录混进 Codex 原始会话历史里，否则会污染被观察对象。

后端提供几类 API：

- `/events`：Codex 上报 trace event。
- `/decision`：Codex 发送 pending outbound request，等待 decision。
- `/policy`：Codex 拉取当前 runtime policy，或后端 push policy。
- `/threads`：UI 查询 thread/request/context timeline。
- `/rewrite`：UI 提交改写。

### 3. 浏览器 UI

UI 不是装饰，它是这个系统的主操作面。它要让你按 thread 看、按 turn 看、按 source 看、按 final request 看，还要能比较 original vs effective。

我理想里 UI 至少有四个视图：

- Thread Timeline：每个 thread 的 turn、request、context update、compaction、tool call。
- Context Tree：本轮上下文按来源树状展开，不是一坨 JSON。
- Request Gate：pending request 的批准/改写界面。
- Policy Editor：运行时开关和规则编辑器。

## 三、核心概念：Original、Assembled、Effective、Sent

要做严谨的调试工具，我建议你强制区分四个状态：

1. **Original**：Codex 内部默认逻辑天然产生的东西。
2. **Assembled**：经过 runtime assembly policy 后，准备组成 prompt 的东西。
3. **Effective**：经过 final gate rewrite 后，准备发送的东西。
4. **Sent**：实际发给模型服务的 payload。

这四层非常关键。

如果你只保存 Sent，你知道模型看到了什么，但不知道 Codex 原本想发什么。

如果你只保存 Original，你知道默认逻辑，但不知道你的 runtime policy 改成了什么。

如果你只保存 Effective，不保存 Sent，你无法排查 transport 层是否又做了变化，比如 WebSocket incremental 只发 delta。

所以每次模型请求都应该有一个 record：

```text
request_id
thread_id
turn_id
kind
original_prompt
assembled_prompt
effective_request
sent_payload
policy_decisions
manual_edits
response_id
status
```

这样你就能回答所有科研问题：官方默认塞了什么？我的 policy 删了什么？我手动改了什么？模型实际收到什么？后续 previous_response_id 是否引用了这个 response？

## 四、provenance 是灵魂：每段上下文都要有来源

你想结构化地把里面的东西都弄出来，关键不只是展示 JSON，而是给每段上下文一个来源身份。

现在 Codex 里很多 fragment 是用 marker 包起来的，比如 `<permissions instructions>`、`# AGENTS.md instructions for ...`、`<environment_context>`。这对人读有帮助，但不是机器级 provenance。你需要的是每个 fragment 在 Rust 结构里都有 metadata：

```text
fragment_id
source_kind
source_path
source_module
role
priority
scope
lifecycle
content_hash
generated_at
```

`source_kind` 可以是：

- model_base_instructions
- model_personality_template
- config_instructions
- config_developer_instructions
- agents_md
- permissions_instructions
- sandbox_instructions
- collaboration_mode
- skill_instructions
- plugin_instructions
- environment_context
- tool_spec
- conversation_history
- compaction_summary
- user_message
- assistant_message
- tool_output
- guardian_policy
- memory_context
- app_context
- dynamic_tool

`lifecycle` 可以是：

- initial_context
- per_turn_update
- persistent_history
- transient_request_only
- compacted
- restored_from_rollout
- restored_from_remote_response

有了这些，UI 才能真正像调试器一样工作。你可以点开一段内容，看它来自哪个 Rust 模块、哪个文件、哪个 config、哪个 AGENTS.md、哪个 thread history item。你也可以按 source kind 一键禁用。

这比“最终 JSON 编辑器”强太多。

## 五、运行时改变拼装逻辑：Assembly Policy

你说“如果现在不支持，我也要让它支持”。那我认为核心就是加一个 Assembly Policy 层。

Codex 当前逻辑大概是：根据 config 和 state，在各个地方 if/else，然后 push developer_sections、contextual_user_sections、history items、tools。这个逻辑分散在 session/context manager/client/tools 等模块里。你可以硬改这些 if，但那不适合运行时调试。

更干净的是：每个候选 fragment 先注册到一个 `ContextAssemblyPlan`，然后 policy 决定 include/exclude/rewrite/reorder/role-change。

也就是从：

```text
代码直接 push 某段 developer text
```

变成：

```text
代码产生一个候选 fragment，带 provenance 和默认行为
policy engine 对候选 fragment 做决策
assembler 输出最终 input items
```

每个候选 fragment 可以有默认属性：

```text
id: permissions.current_policy
role: developer
source_kind: permissions_instructions
default_enabled: true
content: ...
```

policy 可以说：

```text
source_kind == permissions_instructions => exclude
source_kind == agents_md and path contains /third_party/ => exclude
source_kind == environment_context => role = user
source_kind == tool_spec and tool_name != shell => exclude
source_kind == model_base_instructions => replace with custom text
```

这样你不是在最后删字符串，而是在拼装前改变逻辑。Codex 内部也知道 effective context 变了，后续 token estimate、context baseline、incremental request 判断都更一致。

第一版 policy 不需要做复杂 DSL，可以是 JSON rules：

```json
{
  "rules": [
    {"match": {"source_kind": "permissions_instructions"}, "action": "exclude"},
    {"match": {"source_kind": "agents_md"}, "action": "manual"},
    {"match": {"source_kind": "model_base_instructions"}, "action": "replace", "content": "..."}
  ]
}
```

UI 上就是一堆开关和规则表。

## 六、Request Gate 仍然必须存在

即使有 Assembly Policy，最终出站 gate 仍然需要。原因是：

第一，它是最后保险。无论内部哪层漏了，最终 gate 都能让你看到模型实际将要收到什么。

第二，它支持手动实验。你临时想改一句，不应该必须写 policy rule。

第三，它支持第三方路径。某些请求可能不是标准 context assembler 产出的，比如 compact、prewarm、guardian、subagent、memory job。最终 gate 可以兜住所有模型请求。

第四，它是审计边界。你可以证明“没有经过批准的请求不会发出去”。

所以完整设计里应该两层都有：

- Assembly Policy 控制生成过程。
- Outbound Gate 控制最终发送。

这就像编译器：前面有 AST transform，最后还有 codegen output review。

## 七、请求范围要非常明确：哪些请求必须受控

如果你追求“每一时、每一刻我发出去的东西都知道”，那就不能只拦主 chat。需要定义 model request taxonomy。

Codex 可能有这些 request kind：

- main_turn：用户一轮普通对话。
- continuation：模型需要继续生成。
- compact：本地或远程压缩上下文。
- compact_remote_v2：新的压缩路径。
- startup_prewarm：预热请求。
- subagent：spawn agent 请求。
- guardian_review：安全审查请求。
- memory_generation：记忆生成或剪枝。
- realtime：语音/实时路径。
- tool_related_model_call：某些工具内部如果会调模型。
- unknown：没归类的兜底。

完整控制面应该默认拦所有 model request，但 UI 允许按 kind 配置：observe、auto-allow、manual、deny。

科研模式下我会建议默认：

```text
main_turn: manual
compact: manual 或 deny
subagent: manual
guardian_review: observe/manual
autonomous background: deny or observe
unknown: manual
```

这样你不会被后台请求悄悄改变状态。

日常模式下可以：

```text
main_turn: observe
compact: observe
subagent: observe
unknown: manual
```

## 八、history 和 thread store：不要只改历史，要有实验分支

你提到 thread，每个话题一个新线程，历史 append。这里最干净的做法不是直接修改原 rollout，而是引入“实验分支”的概念。

为什么？因为如果你直接改 Codex 的 rollout JSONL，原始事实就丢了。你之后不知道某段上下文是 Codex 生成的、你手动改的、policy 自动改的，还是后端迁移脚本改的。科研 debug 最怕这个。

所以我建议：

- Codex 原始 rollout 保持 append-only，不主动改历史。
- Gateway 后端保存 overlay：某个 thread、某个 turn、某个 fragment 被隐藏/替换/重排。
- 请求构造时读取 overlay policy，生成 effective context。
- 如果你想把某个改写固化，就创建一个 forked experimental thread。

这类似 Git：原始 thread 是 main，debug rewrite 是 working tree overlay，确认后可以 branch。

UI 可以有按钮：

- Apply for this request only。
- Apply for this thread from now on。
- Create experimental fork。
- Export effective prompt。
- Reset overlay。

这样既能掌控，又不污染原始数据。

## 九、能不能“只出现我期望的东西”

可以，但要分级。

### Level 0：普通 Codex

默认内置 prompt + 配置 + 历史 + tools。不可见，或者只能从日志/rollout 事后查。

### Level 1：Observe

所有请求可视化，但不阻断。你知道发了什么，但不能保证发之前看过。

### Level 2：Manual Gate

所有请求发出前必须等你批准。你能保证模型不会看到你没看过的请求。

### Level 3：Assembly Policy

你定义哪些源头允许进入上下文。比如科研模式只允许：

- 你当前输入的 user message。
- 你显式选择的 files/context。
- 你写的 system/developer instruction。
- 你允许的工具 schema。

其他全部默认 exclude。

### Level 4：Hermetic Experiment Mode

完全实验模式：不读 AGENTS，不读 skills，不读 plugins，不注入 permissions，不注入 environment，不使用 prior thread history，不使用 remote model catalog prompt，禁用 compaction，禁用 background jobs。每次请求都由你在 UI 里明确构造。

这个模式最接近你说的“只出现我期望的东西”。它本质上是把 Codex 当成一个模型请求工作台，而不是 coding agent 产品。

我认为你最终会需要 Level 3 和 Level 4。Level 3 用于日常 debug，Level 4 用于科研实验。

## 十、Hermetic Experiment Mode 应该怎么定义

这是我觉得最值得做成明确模式的东西。

Hermetic 模式下，Codex 不应该自动注入任何非用户显式允许的上下文。默认 request 只包含：

- 你在 UI 中设置的 base instructions。
- 当前 user message。
- UI 中手动 attach 的 context items。
- UI 中勾选启用的 tools。

默认禁用：

- bundled model base instructions。
- model personality template。
- AGENTS.md。
- permissions instructions。
- collaboration mode instructions。
- environment context。
- skills instructions。
- plugins instructions。
- memory context。
- prior thread history。
- compact summary。
- startup prewarm。
- background model calls。
- remote model catalog instructions。

这不是日常 coding 模式，但对科研非常干净。你可以一眼知道模型输入来自哪里，因为所有来源都是你显式添加的。

Codex 内部仍然可以保留工具执行能力，但工具暴露也要显式勾选。比如你只想研究 shell tool，就只暴露 shell tool。你不想模型知道 apply_patch grammar，就不暴露 apply_patch。

这个模式最好不要叫“disable everything”，而叫 `experiment_mode` 或 `hermetic_context_mode`。它不是安全模式，是实验可重复性模式。

## 十一、为什么官方默认值在科研里会是噪声

你说“万一我在做科研，不是纯代码工作，那些不都是噪声干扰？”这是非常准确的。

产品默认 prompt 通常服务于产品目标：让 agent 更稳定地写代码、更符合安全策略、更会使用工具、更会遵守开发流程。这些 prompt 对最终行为影响巨大。比如它可能让模型默认偏好改代码、默认读文件、默认用计划、默认遵守 AGENTS、默认用某种语气、默认把自己定位成 coding agent。

如果你的研究问题是“模型在某种最小 instruction 下如何行为”，那这些默认 prompt 就会污染实验。

如果你的研究问题是“工具 schema 对行为的影响”，那其他 developer instructions 也是干扰。

如果你的研究问题是“同一 user prompt 在不同 base prompt 下的差异”，那 Codex 自动注入的 thread history、AGENTS、permissions 会改变变量。

所以科研模式必须支持把上下文来源全部结构化列出来，并允许一键清空。否则你不能确认实验输入。

这也是为什么我支持你做这个东西：它不是“想绕过官方默认”，而是为了建立可观测、可重复、可审计的实验环境。

## 十二、前端 UI 的理想形态

如果要做得完整，UI 不能只是一个 JSON 文本框。它应该像浏览器 DevTools + prompt IDE + approval queue。

我会设计几个区域。

### 1. Global Mode Bar

显示当前模式：

- Normal Observe
- Manual Approval
- Policy Controlled
- Hermetic Experiment

显示后端连接状态、Codex process id、active thread、pending requests。

### 2. Source Matrix

一个矩阵列出所有 context source：

```text
Model base instructions       enabled/manual/disabled
Config instructions           enabled/manual/disabled
Developer instructions        enabled/manual/disabled
AGENTS.md                     enabled/manual/disabled
Permissions instructions      enabled/manual/disabled
Environment context           enabled/manual/disabled
Skills                        enabled/manual/disabled
Plugins                       enabled/manual/disabled
History                       enabled/manual/disabled
Compaction                    enabled/manual/disabled
Tools                         enabled/manual/disabled
```

每一项可以点开看当前内容、来源路径、最近注入时间。

### 3. Assembly Graph

展示本轮 prompt 是怎么拼出来的：

```text
base_instructions
  <- model catalog / config override
input
  <- initial developer bundle
  <- AGENTS.md
  <- permissions instructions
  <- history item #1
  <- current user message
tools
  <- shell tool
  <- apply_patch tool
  <- dynamic tools
```

这比 raw JSON 有解释力。

### 4. Request Inspector

展示 Original / Effective / Sent 三栏 diff。

你可以看到：Codex 原本生成了什么；policy 改了什么；你手动又改了什么；最后发出去的是什么。

### 5. Pending Approval Queue

每个 pending request 可以：

- Allow
- Deny
- Edit and send
- Send as hermetic
- Save as preset
- Fork thread
- Export JSON

### 6. Policy Editor

提供可视化规则，不要求一开始写 DSL。比如：

- Disable all AGENTS.md。
- Strip environment context。
- Replace base instructions with preset。
- Keep only last N user messages。
- Disable tool descriptions except names。
- Require manual approval when tool count > 0。
- Require manual approval for compact requests。

```text
final_action
order_index
```

`requests` 保存：

```text
request_id
thread_id
kind
status
model
created_at
approved_at
sent_at
original_json
effective_json
sent_json
response_id
```

`policies` 保存当前 runtime policy 和历史版本。这样你能回溯：“当时为什么这段被删了？”

## 十四、Rust 侧怎么最小侵入地演进

如果直接大改 Codex context manager，风险很高。我建议分三期。

### Phase 1：Outbound Request Gate

只在出站前加 hook。把完整 `ResponsesApiRequest` 和 metadata 发给后端，等待 decision。支持 observe/manual/rewrite。这个最快有价值。

### Phase 2：Provenance Event Trace

不改变拼装逻辑，只在 fragment render 或 push 时上报 trace。比如 permissions fragment render 时上报 source_kind；AGENTS render 时上报 path；tools build 时上报 tool name。UI 开始能解释来源。

### Phase 3：Assembly Policy

重构 context assembly，让每个 fragment 先进入 plan，再由 policy engine 决策。这个最强，但也最需要设计。

这个顺序很重要。你不要一上来就改拼装逻辑，否则会在上游复杂度里陷太深。先拿到最终请求控制权，再慢慢把 provenance 和 policy 接进去。

## 十五、哪些地方要特别小心

### 1. WebSocket incremental

如果 gateway 改写 request，Codex 内部记录 last_request 时必须记录改写后的 request。否则 previous_response_id 增量逻辑会错。

### 2. Prompt cache key

当前 request 里有 `prompt_cache_key`，一般是 thread id。如果你用同一个 thread id 发送完全不同的 effective prompt，服务端 prompt caching 可能让实验解释变复杂。科研模式下也许应该允许禁用或改写 prompt_cache_key。

### 3. Compaction

Compaction 会把历史变成摘要，是上下文可解释性的敌人。科研模式下我会默认禁用 compaction，或者 compaction request 也必须手动批准。否则你会看到某些内容“不是直接历史，但从摘要里进来了”。

### 4. Tools

工具 schema 是 prompt 的一部分。很多模型行为被 tool description 强烈影响。Hermetic 模式下工具必须显式启用。

### 5. Developer role 和 system/instructions 优先级

Responses API 顶层 `instructions` 和 `input` 里的 developer message不是同一种东西。UI 必须清楚展示 role 和位置，不能把它们揉成一个字符串。

### 6. 回写历史

我再次强调：不要第一版回写 Codex rollout。用 overlay 和 fork。回写会毁掉可审计性。

### 7. 后端安全

这个控制面能看所有 prompt 和文件上下文，必须本地绑定，最好带 token。不要默认监听公网或局域网。

## 十六、你说“官方默认塞几个东西”这个问题怎么彻底解决

最彻底的解决不是去删官方默认，而是让所有默认 source 都变成可见、可开关、可替换。

比如 UI 里明确列出：

```text
Builtin model instructions: ON
Collaboration mode template: ON
Permissions instructions: ON
AGENTS.md: ON
Environment context: ON
Tool instructions: ON
History replay: ON
```

你切到科研模式：

```text
Builtin model instructions: OFF
Collaboration mode template: OFF
Permissions instructions: OFF
AGENTS.md: OFF
Environment context: OFF
Tool instructions: OFF unless selected
History replay: OFF unless selected
```

然后每次 request inspector 都显示：

```text
Included sources: user_message, custom_base_instructions
Excluded sources: builtin_model, agents_md, permissions, environment, tools, history
```

这才叫掌控。不是“我猜它没塞”，而是系统告诉你“哪些源头被排除了”。

## 十七、我对“改变拼装逻辑”的具体建议

最终你应该把 Codex prompt assembly 从隐式 push 改成显式 plan。概念上像这样：

```text
ContextCandidate
  id
  source_kind
  default_role
  default_priority
  content
  provenance

ContextAssemblyPlan
  candidates: Vec<ContextCandidate>

ContextPolicyDecision
  include | exclude | rewrite | require_manual | change_role | reorder

ContextAssembler
  plan + policy -> assembled input
```

这会让 Codex 内部变得更适合实验。任何地方想加上下文，不再直接 push 字符串，而是注册 candidate。policy engine 统一裁决。

这比在每个地方加 `if debug_mode { ... }` 干净。否则你会得到一堆散落开关，后面维护很痛苦。

## 十八、最完整的运行模式矩阵

我会定义四个模式，方便你切换：

### Normal

Codex 原样工作。gateway 不启用。

### Observe

Codex 原样工作，但所有 request、fragment、decision 都记录到 UI。适合日常观察。

### Governed

启用 assembly policy。Codex 根据 UI 规则生成上下文。出站可自动批准或手动批准。

### Hermetic

默认所有自动上下文源关闭。只有 UI 显式允许的 source 能进入请求。所有 model request 默认手动批准。

这个模式矩阵很清晰，而且能兼容你日常写代码和科研实验。

## 十九、我会怎样判断这个系统成功

成功标准不是“能改 JSON”。成功标准应该是：

1. 任意一次模型请求都能在 UI 中找到完整 original/effective/sent 记录。
2. 任意一段上下文都能看到 source_kind 和来源路径/模块。
3. 你可以一键切到 hermetic 模式，确认只有你选择的内容进入模型请求。
4. 手动 approval 开启时，没有未批准请求能发出。
5. 后端断开时，行为按 fail-open/fail-closed 明确执行。
6. 改写不会污染原始 Codex rollout，除非显式 fork。
7. WebSocket incremental、compaction、subagent、guardian 等非主路径不会偷偷绕过。
8. 实验记录可导出，别人能复现 effective prompt。

如果这些做到，就不是普通 debug 面板了，而是一个真正的 agent runtime observability/control platform。

## 二十、我的推荐路线

如果现在让我给你一个现实路线，我会这样排：

第一步，做出站 gate。目标：你马上能看到和改最终 request。这个价值最大，最短路径。

第二步，加 request kind 覆盖和 pending UI。目标：不让 compact/subagent/background 偷偷绕过。

第三步，加 provenance trace。目标：每段上下文知道来源。

第四步，引入 source matrix 和开关。目标：运行时禁用某类 source。

第五步，重构 assembly plan/policy。目标：真正改变拼装逻辑。

第六步，Hermetic mode。目标：科研级干净上下文。

第七步，实验 fork/export/replay。目标：可复现。

这个顺序能让你每一步都有可用产物，不会一开始就陷入大重构。

## 最后说我的真实判断

我觉得你这个想法不只是“debug 方便”。它抓住了 agent 客户端里一个很核心的问题：现代 agent 的行为不是由用户输入单独决定的，而是由一堆隐藏上下文、工具 schema、历史、策略、产品默认 prompt 共同决定的。如果这些东西不可见，就很难研究、很难复现、也很难信任。

官方产品默认追求顺滑和成功率，所以会把很多东西藏在背后自动处理。这对普通用户是好事，对研究者和 runtime hacker 是坏事。你现在想做的是把这些隐藏层重新显影。这个方向完全合理。

最干净的完整做法，就是把 Codex 变成一个可仪器化 runtime：

- 每个上下文源都可见。
- 每个拼装决策都可解释。
- 每个请求出站前都可审批。
- 每个改写都可审计。
- 每个实验都可复现。
- 普通模式不受影响。
- 科研模式可以彻底干净。

所以我不会建议你只做抓包，也不会建议你只改 `models.json` 或 `prompt.md`。那些都是局部手段。真正完整的系统应该是“Context Control Plane”。最终请求 gate 是入口，provenance 是眼睛，assembly policy 是手，hermetic mode 是实验室。

如果你要我给一句最短的架构判断：

**在 Codex 内部建立一个结构化 Context Assembly Plan，把所有候选上下文先变成带 provenance 的 fragment，再由运行时 policy 和本地 UI 决定 include/rewrite/exclude，最后所有模型请求经过 outbound gate 审批后发送。这是最干净、最完整、也最适合你这个 fork 的做法。**
